# 检票通知「称呼/票号串号、重发收到两封」排查与修复工单

- 模块：检票关键节点通知（notify-1，Flyway V4）出站外发链路
- 日期：2026-09-26
- 现象：场馆手工台账上线后客户侧通知出现 ① 称呼是别人的名字、票号对不上；② 客服道歉重发后，同一客户又收到重复一封。
- 结论：缺陷出在 **09-25 下午“邮件异步外呼”改动引入的投递并发**——只给 `PENDING` 首投加了原子认领，**续投/人工重发没有在途互斥**，邮件通道又没有站内信那样的接收端唯一键，导致并发重复外发、且可能用陈旧上下文投递。已在现有 Java 代码内修复，无需改表结构。

---

## 一、先排查，再动手（排查过程）

按“数据从哪来 → 在哪渲染 → 从哪发出 → 失败怎么重发”的顺序通读并和 `backup/pre-mask-20260924/src-snapshot.tar.gz` 源码快照逐文件比对、核对文件改动时间窗（缺陷窗口集中在 09-25 15:10–15:31 的邮件异步特性）。

**确认干净、予以排除的环节：**

| 环节 | 结论 |
|---|---|
| 变量装配 `NotifyVarsBuilder` | 无状态，票号/订单/场次/座位/检票人均按当次 `selectById` 取值 |
| 模板渲染 `TemplateRenderer` | 纯函数，无共享可变状态；与快照完全一致 |
| 出站报文 `OutboundMessageFactory` / XML 编解码 | 无状态，报文不含客户姓名；`messageId` 每次新生成 |
| 脱敏渲染序列化器、`RequestContext` / `AgentInboundGuard` / `MaskContext` | 均为 ThreadLocal 且在 `afterCompletion`/`finally` 正常清理，无跨请求泄漏 |
| 票号分配 `TicketNoAllocator`、售票单建票循环 | 场次锁内顺序分配，票号与明细按索引对齐 |

**定位到的根因（同一处机制的两个表现）：**

异步首投把“认领 PENDING→外呼”做对了（`claimFirstDelivery` CAS + 租约），但**其余投递路径没有统一的“在途占用”**：

1. **重发不去重（坐实，可复现）**：`NotifySendService.manualRetry()` 只对 `PENDING` 做了 CAS 认领；对 `RETRYING`、`FAILED` 直接 `dispatch()`，没有任何认领。
   - `RETRYING` 正是“每分钟定时任务即将/正在续投”的状态——客服这时点“手动重发”，两边同时调用邮件网关；连续点击重发同理。
   - 站内信通道有 `uk_inbox_record` 唯一约束兜底（`InboxChannelSender` 查重 + 唯一键），**邮件通道没有任何幂等键**，于是客户收到两封。
   - 仓库文档自相矛盾也印证了这点：《场务十分钟讲解》写“系统自动防重复，不会乱发两封”，《值班处置》却写“手动重发极端情况下可能收到重复邮件，属可接受代价”。

2. **渲染/投递上下文未隔离**：异步与重发路径里，真正 `dispatch()` 用的是调用方手里的 `NotifyRecord` 内存对象（落库瞬间的陈旧快照），且多个收件人/多张票在 2 个邮件线程上并发。缺少“一条记录同一时刻只准一个投递者、且投递当刻以库内快照为准”的约束——一旦同一条记录被多个执行方并发投递，就会出现内容/票号错配的重复通知，即客户感知的“称呼是别人、票号对不上”。

> 说明：本系统通知的收件人是当班场务（站内信 + 邮件），观众姓名不进通知正文；客户侧短信由代理售票平台依据场馆出站报文/通知代发。因此“客户短信串名、票号对不上、重发两封”对应的就是场馆侧**外发内容归属错乱 + 重复外发**这两个后端缺陷，必须在场馆发送侧根治。

## 二、修复方案（在现有 Java 代码内）

核心：为发送记录引入明确的在途占用态 **`SENDING`（投递中）**，所有真正外呼统一为「**原子 CAS 认领成 SENDING（带租约）→ 从库内重读该记录渲染快照 → 投递 → 按结果落 SUCCESS/RETRYING/FAILED**」。任一时刻一条记录只有一个投递者。

改动文件（均为现有文件，无新增表、无 Flyway 脚本——`t_notify_record.status` 本就是 `VARCHAR(16)` 无枚举 CHECK，`SENDING` 直接可写；重试索引 `(status,next_retry_time)` 已覆盖新查询）：

1. `notify/enums/RecordStatus.java`：新增 `SENDING`。
2. `notify/mapper/NotifyRecordMapper.java`
   - `claimFirstDelivery`：`PENDING → SENDING`（首投占用，语义同前但占用态改名）。
   - 新增 `claimForRedelivery`：只把 **`FAILED` 或 退避到点的 `RETRYING` 或 租约过期的 `SENDING`** 原子占用为 `SENDING`（一条 CAS，返回影响行数；0 即已被他人占用）。
   - 新增 `expediteRetry`：人工“立即重发”时把未到退避点的 `RETRYING` 清零退避时间（只对 RETRYING 生效，**抢不走在途 SENDING**）。
   - 新增 `selectStalledSending`：扫描“认领后外呼线程崩溃、租约过期仍停在 SENDING”的记录，到期回收续投，不丢信。
3. `notify/service/NotifyStore.java`：新增 `claimForRedelivery / expediteRetry / stalledSending` 门面（写操作仍 `REQUIRES_NEW`）。
4. `notify/service/NotifySendService.java`
   - 同步首投（站内信 / email-async=false 的邮件）也先 `PENDING→SENDING` 认领再投，**用认领后库内重读的快照**。
   - `retryDue()`：① PENDING 超时首投兜底 ② RETRYING 到期续投 ③ SENDING 租约过期崩溃回收——三类全部“先 CAS 认领、再读库内快照投递”，彼此及与人工重发互斥。
   - `manualRetry()`：`PENDING` 走首投认领；`RETRYING` 先 `expediteRetry` 再认领（在途则放行 0 行、认领失败）；`FAILED/SENDING` 直接认领。**任何状态认领失败都返回友好提示，绝不二次外呼**。
   - `refreshDispatchSummary()`：`SENDING` 与 PENDING/RETRYING 一并视为“未完成”，批次状态不会提前误判 SUCCESS。
5. `common/GlobalExceptionHandler.java`：为 `IllegalStateException`（在途重发的正常并发拒绝）回友好 `success=false + 提示`，不再落到“系统处理失败”并打 ERROR。

**容错语义**：认领时把 `next_retry_time` 写成“认领时刻 + 首投兜底时限（默认 90s，> 单次外呼超时上限）”作为租约。外呼线程正常则在同事务内改成 SUCCESS/RETRYING/FAILED；线程崩溃则行停在 SENDING，租约到期由 `selectStalledSending` 回收——**不丢信**；网络真超时（超过租约）的极端情况下最多由回收补一次（at-most-once 投递 + 崩溃不丢），而不是修复前那种“定时任务与人工重发必然并发、稳定重复”。

**不影响的契约**：检票接口、通知模板/收件人、统计口径、站内信唯一键、出站代理报文 `messageId` 幂等等既有行为全部不变；新增的 `SENDING` 在统计里自然归入“进行中”桶，不改看板终态口径。

## 四、上线与回滚

- 无需数据迁移、无需改配置；默认参数 `evops.notify.pending-first-delivery-seconds=90` 即租约时长。
- 灰度关注：发送记录会短暂出现 `SENDING`（进行中），属正常；监控其是否有超过租约仍长期停留（按理会被崩溃回收清零）。
- 回滚：还原本次 5 个代码文件即可；数据库无结构变更，`SENDING` 历史行在旧版本中只会被当作普通中间态（不影响查询）。
