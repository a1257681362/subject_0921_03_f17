## 二、排查结论（先排查，后动手）

排查对象不是源码的"想当然"，而是**实际部署的产物** `target/evops-base-0.1.0-SNAPSHOT.jar`（2026-09-25 构建）。将其在本机启动，连真实库 `./data/evops` 走完整 HTTP 链路。

### 结论 1：当前服务端产出的 ZIP，中文条目名是标准 UTF-8 且带 EFS 标志位 —— 正确

- ZIP 写入处：`TicketZipStreamer` 用 `new ZipOutputStream(out, StandardCharsets.UTF_8)`。JDK 在 UTF-8 字符集下对含非 ASCII 的条目自动置 EFS（general-purpose bit 11 = `0x0800`）。
- 真实下载 `/tmp/real.zip` 后手工解析中央目录原始字节：

  | 条目 | 标志位 | EFS | 名字原始字节 |
  |---|---|---|---|
  | `TSH001000000004/票根凭证_TSH001000000004（已检票）.txt` | `0x0808` | ✅ | 正确 UTF-8（`E7 A5 A8 E6 A0 B9…`） |
  | `TSH002000000001/天鹅湖票根_TSH002000000001.txt` | `0x0808` | ✅ | 正确 UTF-8 |
  | `下载清单.txt` | `0x0808` | ✅ | 正确 UTF-8 |

  用认 EFS 的解析器（Python zipfile）解压，中文 100% 还原。
- 反编译部署包内 `TicketZipStreamer.class`，确认字节码确实调用 `ZipOutputStream.<init>(OutputStream, Charset)` 且加载 `StandardCharsets.UTF_8`，与源码一致。
- 源码比对：`backup/pre-mask-20260924/src-snapshot.tar.gz`（2026-09-24）中的 `TicketZipStreamer.java`、`TicketAttachmentService.java` 与当前**逐字节相同**，即该 UTF-8 行为自 ticket-2 上线起一直如此，不是最近被改坏。

### 结论 2：上传入库的中文文件名完好，库底账是正确中文

- JDBC 直查 H2 `t_ticket_attachment.file_name`，码点正确：`天鹅湖票根` = `5929 9E45 6E56 7968`，无下划线、无替换符。
- 真实 multipart 上传两种浏览器形态都验证：
  - curl 直接发 UTF-8 文件名 → 入库 `入场凭证_中文测试.txt`；
  - 浏览器形态 `filename="____.pdf"; filename*=UTF-8''%E6%B5%8F…`（RFC 5987）→ 入库 `浏览器发票_中文.pdf`。
- 同一票号传两个同名中文文件 → 包内 `重复名.txt` / `重复名(2).txt`，重名加序号逻辑对中文有效。

### 结论 3："下划线"不是编码乱码，而是解压/保存端的非 ASCII 清洗

- 故意**无视 EFS 位**，把 UTF-8 条目名按 GBK / CP437 错误解码，得到的是 `绁ㄦ牴鍑`、`τÑ¿` 这类**乱码字符**，**绝不会得到下划线**。
- 全仓搜索，把非 ASCII 转成 `_` 的逻辑只有一处：`TicketAttachmentController.asciiFallback`。它**只用于最外层 ZIP 包名响应头里的 ASCII 兜底 `filename="…"`**（同时给了正确的 `filename*=UTF-8''演出票附件_时间戳.zip`）。**ZIP 内部条目名不经过任何清洗**；全项目也只有这一条打包路径。
- 本机 Info-ZIP `unzip` 即不认 EFS，列出为乱码（非下划线），从侧面印证现象取决于解压端。
- 结论：客户看到的"全变下划线 + 无法对应票号"，最可能是 ① 解压/保存工具只取了 ASCII 兜底名或自行把非 ASCII 清洗为 `_`；或 ② 客户手里的是**更早的构建**——"票号目录 + 文件名内嵌票号 + 下载清单"是 ticket-2 才具备的，当前版本即使文件名被清洗，纯 ASCII 的票号目录 `TSH…/` 与清单仍可对应票号，不会"只能挨个重命名"。

### 结论 4：两个被点名的校验，实测都在开流前/生成时生效

- **单包上限前置校验**：51 个票号在**打开响应流之前**被拒，返回 `200 + {"success":false,"message":"单包最多 50 份，本次 51 份，请分批下载"}`，`Content-Type: application/json`，**不产出半截 ZIP**；空白票号返回"请至少选择一个票号"。硬上限在 `TicketAttachmentService` 用 `Math.min(配置, HARD_TICKET_LIMIT=50)` 兜底，配置无法调大到 50 以上。
- **清单生成校验**：每个包根目录必带《下载清单.txt》（UTF-8 **带 BOM**，Excel 直开不乱码），表头 `序号/票号/包内文件`，逐行映射；无附件票号单列"以下票号未检索到附件"，物理缺失单列"物理文件缺失（未打入包内）"，均不中断整包。

## 三、本次改动范围（已最小化，生产代码零改动）

既然当前服务端标准正确，**不改生产逻辑**，只把"中文必须以 UTF-8 + EFS 落包"这一约定从"靠人记得"变成"测试锁死"，防止以后有人把 `ZipOutputStream` 的 UTF-8 构造器改回默认字符集导致真退化。

| 类型 | 文件 | 改动 |
|---|---|---|
| 新增测试 | `src/test/java/com/evops/ticket/attachment/web/TicketAttachmentZipWebTest.java` | 新增用例 `zipStream_chineseEntries_areRawUtf8WithEfsFlag_bitLevelRegression`：真实 HTTP 下载 ZIP 后**手工解析中央目录原始字节**，断言含非 ASCII 的条目 ① 置 EFS（bit11=`0x0800`）；② 名字原始字节即 UTF-8 且可无损往返；③ 关键中文样本名/清单名按 UTF-8 精确还原。配套新增 `readCentralDirectory` / `readUInt16` / `CentralEntry`。 |
| 文档 | `docs/acceptance/附件整批下载中文名下划线-排查与回归工单.md` | 本变更单。 |

- **不新增依赖、不改配置、不改 SQL、不动 `src/main` 任何生产文件。**
- 既有用例 `TicketAttachmentZipWebTest`（6 个，历史报告 6/6 通过）已覆盖：401、上传/列表/单下载中文名、ZIP 票号目录与中文条目、无附件票号入清单、超 50 开流前拦截、逻辑删除。新增用例把"中文条目"的校验从"解码后比对"升级为"**字节与标志位比对**"，强度更高、且不受解压库解码策略影响。
