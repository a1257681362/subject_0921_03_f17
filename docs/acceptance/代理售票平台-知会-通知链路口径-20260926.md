# 致代理售票平台：场馆通知链路口径知会（2026-09-26）

> 知会目的：场馆侧近期排查了一起"客户短信称呼错人、票号对不上"的报障，结论与贵平台联调口径相关，特同步如下，免得双方联调时互相猜。
> 联系人：场馆票务研发；生效日期：2026-09-26。

## 一、一句话结论

**本次报障的根因不在系统接口，而在手工台账底账；场馆→平台的出站报文协议、字段、幂等口径均无变化，贵平台无需任何改动。**

## 二、背景与排查结论

- 场馆曾有一次手工台账（系统外人工登记补录），底账中客户与票号的对应关系被记串。此后按错乱底账发出的客户短信出现"称呼是别人的名字、票号对不上"。
- 场馆侧已完成排查：通知/报文链路对每张票**独立取数、独立渲染、逐字快照**，不存在把 A 票数据写进 B 票报文的代码路径；现场库历史报文逐条核对，归档票号列与报文内 `<ticketNo>` 全部一致。
- 场馆侧同时修复了一处内部联调测试配置缺陷（与贵平台无关），并新增回归用例锁住"渲染隔离、重发去重"两条口径，全量 126 个测试通过。

## 三、与贵平台相关的口径（均无变化，请知悉）

| 口径 | 现状 | 贵平台动作 |
|---|---|---|
| 报文协议（XML 结构、命名空间、字段） | 无变化 | 无需调整 |
| 幂等键 | 出站 `messageId` 全局唯一；**重发/补投沿用原 messageId**，不另起新号 | 继续按 messageId 去重即可 |
| 重复投递 | 极端情况下（网络重试）贵平台可能收到同 messageId 的重复报文，属预期"至少一次"语义 | 按 messageId 幂等忽略 |
| 按票补推（人工） | 人工补推会生成**新** messageId（用于历史票补同步），属新业务事件而非重试 | 按新报文正常受理 |
| 空金额节点 | 空=未知（不是 0），显式 `<price>0</price>` 才是零元 | 维持既有口径 |

## 四、客户短信错配的核对建议

贵平台侧客户短信的称呼/票号取自贵平台底账。若再收到类似客诉，建议按以下顺序核对，**不必先怀疑报文串票**：

1. 按票号调场馆归档回查接口（`GET /api/ticket/agent/tickets/{ticketNo}/messages`，需场馆后台令牌）核对场馆实际发出的报文原文；
2. 核对贵平台底账中该票号对应的客户档案，确认是否在手工台账期间被录错；
3. 双方底账对不上的，以场馆票务底账（`t_ticket`）为准逐票更正。

## 五、联调环境注意事项

- 场馆联调环境邮件/短信网关为内置桩（不真发外部短信）；如需联调"批量补录→通知→平台接收"全链路，请提前半天知会，场馆侧安排窗口并提供检票批次号（dispatchId）便于对账。
- 联调中若观察到**同 messageId 重复报文**，请先确认是否为场馆重试（预期行为）；若观察到**不同 messageId 但业务内容重复**，请保留原文并联系场馆研发——那是需要双方一起看的异常。
