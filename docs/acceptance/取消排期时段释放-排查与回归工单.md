## 二、排查结论（先排查，后动手）

### 结论 1：当前代码"取消即释放"行为正确，报障的"延迟释放"在当前代码不复现

取消与再约在**同一把座位行锁**上串行，取消提交的那一刻时段即释放：

- `cancel()`（`CheckinAppointmentService.java:110`）：与预约同一把 `SELECT ... FOR UPDATE` 座位锁 → 置 `status=CANCELLED` → **同一事务提交**。提交成功后该区间立即不再参与冲突判定。
- `create()`（`CheckinAppointmentService.java:69`）：先 `lockSeat()` 加同一把座位锁 → 再查冲突候选 `findActiveCandidates()`，**只取 `status=ACTIVE` 的行**（`CheckinAppointmentService.java:355`）。已取消行（CANCELLED）被状态条件排除，不可能再挡住再约。
- 因为 create 先拿锁、取消先提交，后进入的 create 读到的一定是取消已提交的结果——这是"取消提交后可立即再约"的机制本身，类注释也写明了这一点。

实机验证（真实 jar 启动、真实账号、真实 HTTP，非单测替身）：

| 步骤 | 操作 | 实际返回 | 结论 |
|---|---|---|---|
| 1 | 预约 12-01 10:00-10:30 | `id=1, status=ACTIVE` | 正常 |
| 2 | 取消 id=1 | `status=CANCELLED` | 正常 |
| 3 | **立即再约同一时段** | **`id=2, status=ACTIVE`** | ✅ **取消即释放，无延迟** |
| 4 | 再约同一时段（id=2 仍 ACTIVE） | `success=false`「该座位所选时段已被预约或与相邻预约间隔不足20分钟」 | 冲突检测正常 |
| 5 | 取消 id=2 | `status=CANCELLED` | 正常 |
| 6 | **立即再约同一时段** | **`id=3, status=ACTIVE`** | ✅ 再次确认即时释放 |
| 7 | 占用查询 12-01 全天 | 仅 `id=3` 一条 `ACTIVE` | 历史行保留、仅一条有效 |
| 8 | 取消原因含低危词「加微」（触发 REQUIRES_NEW 留痕事务）后立即再约 | 取消 `status=CANCELLED`（原因打码为「客户要求**信改期」），再约 `id=7, status=ACTIVE` | ✅ 敏感词留痕链路也不延后释放 |

### 结论 2：并发边界 —— 唯一可能看到瞬时"占用"的情形

实机并发（1 个取消 + 8 个同时段再约同时打进）：

```
取消:   success=true, status=CANCELLED
再约:   仅 1 个成功(id=5)，其余 7 个瞬时"occupied/conflict"
最终占用查询: 仅 1 条 ACTIVE   ← 无双约、无残留占用
```

- **顺序操作（取消返回成功后再约）**：永远立即成功（结论 1 的步骤 3/6）。
- **并发操作（再约与取消同时打进）**：再约若在取消提交前先拿到座位锁，会读到取消前的 ACTIVE 而瞬时"占用"；取消提交后重试即成功。这是"取消+重下"两步操作的固有竞态窗口（毫秒级），不是延迟释放。
- 座位行锁保证：同一座位同一时段并发双约**恰好一条成功**，不会出现两条 ACTIVE 叠在一起。

### 结论 3：历史"几分钟后才放出"的最可能成因

当前代码（含 09-24 01:01 源码快照）已具备座位锁串行化，报障症状在此不复现。结合时间线，症状最可能来自：

1. **更老版本**：座位锁串行化（类注释所述"取消提交后可立即再约"）引入之前，取消与再约未串行，并发下再约可读到取消前的 ACTIVE。当前代码已含该修复。
2. **相邻/重复 ACTIVE 预约**：再约报"占用"也可能是因为该座位**另一条** ACTIVE 预约（重叠或首尾间隔不足 20 分钟缓冲）挡住，而非刚取消的那条——取消行本身不参与冲突。
3. **并发竞态**（结论 2）：再约撞上取消未提交的毫秒级窗口。

> 若现场在**当前构建**上仍能稳定复现"取消后顺序再约仍报占用"，请提供：部署的 jar 构建时间、该座位当时全部预约行（`t_checkin_appointment` 按 seat_id 查）、以及再约请求/响应原文。当前排查已覆盖顺序、并发、跨天、敏感词留痕、两种 H2 存储形态，均未复现。

### 结论 4：边界梳理（确认无遗漏）

- 全库无触发器、无定时任务触碰 `t_checkin_appointment`（3 个 `@Scheduled` 任务仅处理代理报文/通知/令牌清理）。
- 座位表 `t_seat` 为纯主数据，无"占用标志"冗余列需同步清理。
- 幂等层（`IdempotentService`）冲突响应不落库、不回放；取消/再约各走独立 X-Request-Id，不会互相回放。
- 预约写入仅 `CheckinAppointmentService.create/cancel` 两处，均经座位锁，无绕过路径。
- 两种 H2 存储形态（内存 MySQL 模式 / 文件默认模式 + AUTO_SERVER，与生产一致）行为一致。

- 现在**取消一个时段后，该时段立即可再约**（取消返回成功即释放），改期按"先取消、再重下"操作即可，无需等待。
