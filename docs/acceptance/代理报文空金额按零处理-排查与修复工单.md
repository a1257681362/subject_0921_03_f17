## 一、报障原话

> 现在的数据要二次加工才能用。代理售票平台回传的报文里某个金额节点为空，系统直接按零处理，票款汇总差了一大截。请安排先排查，属实在当前工作区的 Java 服务内修复缺陷，别拖到下个迭代。空值边界用例；空值语义要有用例锁住。动库之前先备份，脚本在备份库试跑过再上。

## 二、排查结论（先排查，后动手）

### 结论 1：缺陷属实，根因是「空（未知）」被静默兜底成「0」并参与汇总

票款金额从入模到汇总的链路：`SaleItem.price`（DTO）→ `SaleOrderService.create()` → `t_ticket.price` / `t_sale_order.total_amount`。

修复前两处显式把 `null` 兜底成 `BigDecimal.ZERO`：

- `SaleOrderService.java`（旧 104-106 行）订单汇总：
  `items.stream().map(i -> i.getPrice() == null ? BigDecimal.ZERO : i.getPrice()).reduce(ZERO, add)`
- 同方法旧 121 行落票明细：`ticket.setPrice(item.getPrice() == null ? BigDecimal.ZERO : item.getPrice())`
- DTO `SaleItem.price` **没有任何非空/非负约束**（仅 seatId 有 `@NotNull`），控制器 `@Valid` 拦不住空金额。

实证解析行为（用与现场同版本 jackson-dataformat-xml 2.13.5 实测）：

| 报文片段 | 解析结果 | 语义 |
|---|---|---|
| `<price></price>` | `null` | 平台未提供（未知） |
| `<price>   </price>` | `null` | 同上 |
| 节点缺省 | `null` | 同上 |
| `<price>0</price>` | `BigDecimal(0)` | 平台明确给零（赠票/免票） |

即：协议层本来能区分「空=null」与「0=真零」，但入模后被服务层统一抹平成 0，**一张真实售价的票金额缺失，就按 0 计进 total_amount，票款汇总整段少计**——与报障完全吻合。

### 结论 2：入站状态同步报文不消费金额，无需在状态机里改口径

入站仅受理 `TICKET_CHECK/REFUND/VOID`（`InboundAgentService`），只驱动票状态机，不读 `price`。金额唯一落库/汇总入口是售票建档。因此修复点放在「协议空值语义显式化 + 建档入口拒绝空值」，不改入站状态机，影响面最小。

### 结论 3：现场库存量排查结果——本环境底账干净，0 张 0 价票、0 个失真订单

对现场 `./data/evops` 只读排查（脚本 `scripts/fix-null-price-20260925/01_detect_zero_price.sql`）：

- `price=0` 的票：**0 张**
- `total_amount <> Σ票明细` 的订单：**0 个**
- 票款合计 `Σ t_ticket.price = 5080.00`，订单汇总合计 `Σ total_amount = 5080.00`，**两边相等**

故现场库无需数据订正；脚本仍按要求走完「备份 → 备份库试跑 → 上现场」流程并留档，供后续真出现脏数据时直接复用。

## 三、修复内容（不引入新依赖）

1. **协议层空值语义显式化**：新增 `EmptyAwareBigDecimalDeserializer`，挂到 `XmlTicket.price`。
   - 空标签/纯空白/缺省 → `null`（未知）；`<price>0</price>` → `ZERO`（真零）；非数字 → 抛异常按坏报文进异常清单，不静默吞掉。
2. **建档入口拒绝空金额**：`SaleItem.price` 加 `@NotNull`（明确文案「空值表示金额未知，不得按 0 入账」）+ `@DecimalMin(0)`；`SaleOrderService` 服务层再守一道（空值/负数抛 `IllegalArgumentException`，整单回滚，不留半截 0 价数据）。移除两处 `null→ZERO` 静默兜底。
3. 空值≠0 的语义在字段注释、反序列化器注释中写明，指向锁定它的测试。

## 四、空值语义与边界用例（锁住，防回退）
