## 一、报障原话

> 刷新令牌换新后，旧的访问令牌在有效期内依然可用，双端同时操作互不干扰，轮换形同虚设。要求：刷新后旧令牌作废；停用账号令牌失效。先排查再改，接口契约别动。排查结论写进工单，场务要看证据。

## 二、排查结论（先排查，后动手）

### 结论 1：报障属实 —— 这是一个真实缺陷（高危）

双令牌设计里，"轮换一次性"只做到了**刷新令牌**这一半，**访问令牌那一半漏了**：

| 环节 | 修复前实际行为 | 是否符合设计 |
|---|---|---|
| 旧刷新令牌 | refresh 时库内条件更新 `ACTIVE→USED`，再用即 401，重放触发家族连坐 | ✅ 正常 |
| **旧访问令牌** | **refresh 只换发新令牌，没有任何动作吊销旧 JWT；tv 不变、不在黑名单，旧 access 在剩余最长 15 分钟内继续 200** | ❌ **缺陷** |

根因定位（修复前代码）：

- `AuthService.refresh()`（`src/main/java/com/evops/auth/service/AuthService.java`）：只调 `refreshMapper.consume()` 消费旧刷新令牌，随后 `issuePair()` 沿家族签发新对——**全程没有拉黑旧访问令牌的 jti**。
- `AuthService.authenticate()` 对一枚未过期 JWT 的放行条件是：签名有效 → jti 不在黑名单 → 账号 ACTIVE → tv 匹配。刷新不改 tv、旧 jti 又没进黑名单，因此旧 access 四项全过。
- 与登出/改密对比即可看出缺口：登出会把当前 access 的 jti 写 `t_token_blacklist`（LOGOUT），改密会推进 `token_version` 并拉黑当前 access；**唯独 refresh 路径只换不吊销**。
- 数据层也缺少挂钩点：`t_refresh_token` 表没有登记"这枚 refresh 配对的是哪枚 access"，即使想吊销也无从定位。

**影响**：在公共电脑/他人设备上点过一次"刷新登录"，或 access 被复制走，轮换后攻击者手里的旧 access 最长还能正常操作 15 分钟；两端各持一枚有效 access 并行写操作，违背一次性轮换的安全承诺。

### 结论 2：停用账号"令牌失效"——校验链路有效，但系统缺停用入口，且重启用策略有缺口

- `authenticate()`（每次接口请求）、`refresh()`、`login()` 三处**都会**检查 `t_admin_user.status`，实测一旦库里置 `DISABLED`，旧 access、旧 refresh、密码登录**全部立刻 401**（见证据 E-before-3）。"状态拦截"这一环本身是好的。
- 但排查全部管理端代码（`RbacAdminController` / `RbacAdminService`）发现：**系统没有任何停用/启用账号的接口**，`status` 字段只能直接改库，场务/管理员在页面上无操作入口。
- 缺口：若仅靠 status，账号被重新启用（status 改回 ACTIVE）后，停用前那枚 15 分钟内的旧 access（以及未撤销的 refresh）会**复活**。停用是安全处置动作，必须保证"启用 ≠ 旧会话复活"。

### 结论 3：接口契约梳理（确认修复不破坏契约）

- `POST /api/auth/login`、`POST /api/auth/refresh`、`POST /api/auth/logout`、`POST /api/auth/change-password`、`GET /api/auth/me`、`GET /api/auth/menus` 的**路径、请求体、响应体字段、HTTP 语义全部未改**。
- refresh 响应仍是 `TokenPairVO`（accessToken/refreshToken/tokenType/两个 expiresIn/user），字段一个没动。
- 数据库为增量迁移 **V8**（只 `ADD COLUMN` 两个可空列 + 台账双写），老库可平滑升级、存量行为 NULL 安全兼容；不改任何既有列。
- 停用/启用是**新增**两个端点（见下），属于补能力，不改动既有端点。

## 三、修复内容

### 1）刷新轮换时，同步作废旧访问令牌（核心修复）

- 新表列（V8 迁移 `db/migration/V8__refresh_revoke_old_access.sql`）：`t_refresh_token` 增加
  `access_jti`（配对访问令牌的 jti）、`access_expires_at`（配对 access 的自然过期时间）。
- 每次登录/刷新签发新对时，把配对 access 的 jti 与过期时间登记进该刷新令牌行。
- `AuthService.refresh()` 在 `consume()` 成功的**同一事务内**，按登记的 jti 向 `t_token_blacklist`
  写一行 `reason=ROTATED`（与 consume/issue 同生共死，不会出现刷新成功却没拉黑）。
- 于是刷新成功返回的一刻，旧 access 在下一个请求即命中黑名单 → 401；新 access 正常。
  黑名单行只活到该 access 自然过期，由既有每日 03:17 清理任务回收。
- 边界处理：
  - V8 上线前签发的存量 refresh（配对列为 NULL）无法定位旧 access，跳过拉黑、等其 15 分钟自然过期收敛，不影响老库并跑；
  - 配对 access 已自然过期则不再写黑名单；
  - jti 已因登出/改密在黑名单（重复键）时幂等跳过，轮换照常成功；
  - **只吊销被轮换的这一台设备家族**，其他设备的 access/refresh 完全不受影响（证据 E-after-B）。

### 2）补齐 ADMIN 停用/启用账号入口，停用即全量失效、重启用旧会话不复活

- 新增端点（`RbacAdminController`，需 `rbac:manage`，即仅 ADMIN）：
  - `POST /api/admin/rbac/users/{id}/disable` —— 停用账号；
  - `POST /api/admin/rbac/users/{id}/enable` —— 重新启用账号。
- 停用在 `AuthService.deactivateAccount()` 一个事务内做三件事：
  1. `status=DISABLED`——所有接口下一请求即被挡（401，"账号不可用，请重新登录"）；
  2. **`token_version` 自增**——即使日后启用，停用前签发的旧 access 仍因 tv 不匹配继续作废，旧会话不复活；
  3. 撤销该账号**全部设备**的 ACTIVE 刷新令牌——停用期间无法再轮换出新令牌。
- 启用 `activateAccount()` 只恢复可登录状态，不回退 tv、不恢复 refresh；历史令牌继续作废，必须用密码重新登录。
- 防护：ADMIN **不能停用当前登录的自己**（防自锁，返回 success=false 提示）；停用/启用均幂等；非 ADMIN 调用统一 403。

## 五、给场务/值班的操作变化（一句话）

- 以前点"刷新登录"，旧的那枚登录态 15 分钟内还能用；**现在刷新成功的一瞬间，旧登录态立刻失效**，只保留最新这枚——这正是"一次性轮换"应有的表现。自己一台设备正常使用完全无感知，刷新拿到新令牌继续用即可。
- 两台设备（如电脑+平板）各自登录、各自刷新，**互不影响**，不会再像"重放泄露"那样被连坐；只有同一枚旧刷新令牌被重复使用（典型为泄露）才会整条设备链作废。
- 管理员新增**停用账号**能力：人员离职/账号异常时，ADMIN 在权限管理对该账号点停用，对方**手里现有登录态下一秒即掉线（401）、刷新令牌全部作废、密码也登不进来**；日后重新启用，旧登录态也不会复活，必须重新登录。操作详见值班处置文档"一人多岗权限"中的停用/启用章节。
