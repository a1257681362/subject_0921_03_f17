# 联调知会：场馆检票通知/出站「重发去重 + 渲染隔离」修复

- 致：代理售票平台对接团队
- 发：场馆票务（EVOPS）后端
- 日期：2026-09-26
- 关联：场馆侧工单 `docs/acceptance/通知重发去重与渲染隔离-排查与修复工单.md`

## 一句话结论

场馆侧修复了通知/出站外发在“慢网络 + 重试/人工重发”下**可能重复发送、且个别通知票号/称呼错配**的问题。**对平台的接口契约、XML 报文结构、幂等口径均无改动，平台侧无需改造**；联调时不会再看到同一业务被重复推送。

## 为什么要通知你们

此前场馆在“邮件异步外呼”改造中，首投做了去重，但**定时续投与人工重发缺少在途互斥**：网关响应慢时，平台/收件方可能就同一票收到不止一条内容。为避免联调时双方对着重复报文互相猜测原因，特此同步：该行为在场馆发送侧已根治。

## 变更内容（仅场馆内部，均不越接口边界）

- 发送记录新增一个内部状态 `SENDING`（投递中）：一条记录同一时刻只允许一个执行方（异步首投 / 定时续投 / 人工重发 / 崩溃回收）真正外呼，靠数据库原子认领（CAS）保证。
- 真正外呼时一律使用**该记录在数据库里的渲染快照**，不再使用可能陈旧的内存对象——保证票号、订单号、场次、座位、称呼与业务票严格一致。
- 外呼线程崩溃时，记录停在 `SENDING`，租约到期后自动回收续投，**不丢通知**，也不并发重发。

## 对平台方“不变”的部分（重点）

| 项 | 口径 |
|---|---|
| 出站报文结构 | 不变（`<agentMessage>` header/body/ticket 字段与命名空间照旧） |
| `messageId` 幂等 | 不变：每条新报文仍由场馆生成全局唯一 `messageId`；**手动“按票补推”仍是新 messageId**，失败报文“重发”仍用原 messageId |
| ACK 应答 | 不变：`SUCCESS / DUPLICATE / REJECTED`，`correlationId` 回填原 messageId |
| 接口地址 / 鉴权 | 不变 |
| 投递语义 | 仍为至少可达；但场馆侧已消除“同一记录被并发重复投递”，平台正常情况下**一笔业务只收到一条** |

## 联调时请配合/知悉

1. 若仍偶发收到极少量重复（例如对端长时间无任何响应、超过场馆投递租约后的崩溃补偿），以 `messageId` 为准去重即可——这是网络层 at-least-once 的兜底，**不同 messageId 代表场馆确认需要处理的补推**，同 messageId 的重复请回 `DUPLICATE`（现状已如此）。
2. 场馆侧慢响应注入/重试演练时，发送记录会短暂停在 `SENDING`，属正常进行中态，不代表丢单。
3. 如平台收到票号与正文/座位不一致的报文，请保留原文并按 `messageId`、`ticketNo` 反馈场馆——本次修复后该类情况应已绝迹，一旦出现属高优先级问题。
