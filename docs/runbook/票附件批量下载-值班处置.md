# 客服整批下载演出票附件 · 值班常见情况处置（一页速查）

> 适用功能：票附件上传、单个下载、整批 ZIP 下载（`/api/ticket/attachments/zip`）。
> 全部接口必须登录（访问令牌，请求头 `Authorization: Bearer <accessToken>`，有效期 15 分钟）。
> 单包上限 **50 份票号**；ZIP 为**流式生成**，服务端不落临时文件、不占整包内存。

## 接口速记

| 事项 | 方法与路径 | 说明 |
|---|---|---|
| 上传附件 | `POST /api/ticket/tickets/{票号}/attachments`（multipart，字段 `file`） | 单文件 ≤20MB |
| 查某票附件 | `GET /api/ticket/tickets/{票号}/attachments` | — |
| 单个下载 | `GET /api/ticket/attachments/{附件id}/download` | — |
| **整批 ZIP** | `GET /api/ticket/attachments/zip?ticketNos=票号1&ticketNos=票号2` | ≤50 票号，自动去重 |
| 删除附件 | `DELETE /api/ticket/attachments/{附件id}?reason=` | **逻辑删除**，元数据保留 |

## 常见情况与处置

| # | 现象 | 先判断 | 处置 |
|---|---|---|---|
| 1 | 返回 **401「缺少访问令牌/登录态无效」** | 令牌过期（15 分钟）或没带请求头 | 重新登录拿 accessToken 再试；不是故障，不用报运维 |
| 2 | 提示 **「单包最多 50 份，本次 N 份，请分批下载」** | 一次选超了 | 拆成每批 ≤50 个票号，分多次下载；去重后计数，重复票号不占额度 |
| 3 | 提示 **「所选票号均无附件可下载」** | 票号下未传过附件 | 先在票务页核对票号，确认附件已上传；个別票无附件时不报错，会写进清单提示 |
| 4 | **解压后文件名乱码** | 多为老解压工具（如 WinRAR 旧版）编码问题，服务端 ZIP 条目已是 UTF-8 | 用 Windows 10/11 资源管理器直接打开，或换 Bandizip/7-Zip 新版；**不要让后台改名重传**；包内《下载清单.txt》为 UTF-8 带 BOM，Excel 直接打开不乱码 |
| 5 | 清单里出现 **「以下票号未检索到附件」** | 该票确实没有附件，或票号填错 | 与客服核对票号；缺附件的走补传 |
| 6 | 清单里出现 **「物理文件缺失（未打入包内）」** | 元数据在、文件被外部清理/磁盘故障 | 其余文件已正常入包，先给客服用；立即报运维查存储目录（配置 `evops.attachment.storage-dir`，默认 `./data/attachments/`），日志关键字 `票附件物理文件缺失` |
| 7 | 下载到一半中断、ZIP 打不开 | 流式传输中网络抖动/连接被掐，响应已部分写出无法改回错误提示 | 直接**重新点下载**即可（接口只读、可重复）；反复失败再查网络与服务日志 `ZIP 流式生成中断` |
| 8 | 上传报 **「附件超过大小上限」** | 文件 >20MB（容器与业务两道限制） | 压缩/拆分后重传；不要随意调大上限 |
| 9 | 上传报 **「票不存在」** | 票号输错或票已按逻辑删除查不到 | 在票务检索页按票号核实 |
| 10 | 误删附件 | 删除是**逻辑删除**，库里元数据仍在（`deleted=id`），且**物理文件不会被立即删** | 不要自行到库里改；走运维按 id 核查后恢复（数据订正留痕），原文件仍可在存储目录按 `storage_name` 找到 |
| 11 | 中文包名/文件名保存后变下划线 | 浏览器只认了 ASCII 兜底名（极少见） | 响应头同时给了 `filename*=UTF-8''` 编码名，升级浏览器/换 Chrome、Edge 即可 |
| 12 | 多人同时大量打包，系统变慢 | ZIP 虽流式，但磁盘 IO 与并发下载数仍有上限 | 错峰下载；持续高并发报运维评估限流，不要自行改并发参数 |

## 给运维的定位要点（客服转报时附上）

- 配置：`evops.attachment.storage-dir`（存储目录）、`zip-max-tickets`（50，**不允许调大**）、`max-upload-size`（20MB）；可用环境变量 `EVOPS_ATTACHMENT_DIR` 覆盖目录。
- 元数据表：`t_ticket_attachment`（按票号查：`ticket_no`；物理文件名看 `storage_name`；逻辑删除看 `deleted`）。
- 关键日志：`票附件存储目录`（启动确认目录）、`票附件物理文件缺失`、`ZIP 流式生成中断`。
- 存储目录要纳入**磁盘容量监控与备份**；换服务器/迁盘时先停写、整体拷目录再改 `EVOPS_ATTACHMENT_DIR`，文件缺失会直接导致第 6 类工单。
- 版本与台账：附件表为 Flyway **V3**，启动日志应见「Schema 台账对账一致」；出现 `flyway-3` 对账 ERROR 先别营业，按既有 Schema 对账流程处理。

## 绝对不要做

- 不要直接把附件文件放到存储目录手工"补数据"而不写 `t_ticket_attachment`（打包只认元数据）。
- 不要手工重命名存储目录里的文件（文件名是服务端 UUID，改名即"文件缺失"）。
- 不要为绕过 50 份限制调大 `zip-max-tickets`——这是例会敲定的硬上限（代码内再封顶 50）。
