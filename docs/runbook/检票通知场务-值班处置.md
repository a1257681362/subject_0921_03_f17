# 检票关键节点通知场务 · 值班常见情况处置（一页速查）

> 适用功能：观众检票后自动通知当班场务——**站内信 + 邮件双通道**、模板变量渲染、
> 发送记录入库、失败自动重试 2 次、发送结果统计。
> 管理接口必须登录（`Authorization: Bearer <accessToken>`，有效期 15 分钟）。
> 站内信场务用工号登录后台即可查收；邮件走企业邮件出口网关（演示环境为内置桩 `/mail-stub`）。

## 接口速记（前缀 /api/ticket/notify）

| 事项 | 方法与路径 | 说明 |
|---|---|---|
| 场务查本人站内信 | `GET /inbox/messages?readFlag=0` | 0 未读 / 1 已读 / 不传全部 |
| 未读数（角标） | `GET /inbox/unread-count` | 只统计本人工号 |
| 标记已读 | `POST /inbox/messages/{id}/read` | 幂等，可重复点 |
| 发送记录分页 | `GET /records?ticketNo=&channel=&status=` | 通道 INBOX/EMAIL；状态见下 |
| 发送记录详情 | `GET /records/{id}` | 含**渲染后标题/正文快照**、模板版本、回执、错误原因 |
| 失败手动重发 | `POST /records/{id}/retry` | FAILED/RETRYING 可立即补达 |
| 发送统计 | `GET /stats?eventCode=TICKET_CHECK&from=&to=` | 批次 + 通道两层计数 |
| 模板维护 | `GET/POST /templates`、`PUT /templates/{id}` | 改文案自动升版本，**不影响已发** |
| 收件人维护 | `GET/POST /recipients`、`PUT /recipients/{id}` | 工号、邮箱至少一个 |

记录状态：`SUCCESS` 成功 / `RETRYING` 退避重试中 / `FAILED` 重试 2 次耗尽 / `SKIPPED` 不具备该通道（如没邮箱）。
批次状态：`SUCCESS` 双通道都成 / `PARTIAL` 一成一败 / `FAILED` 都败。

## 常见情况与处置

| # | 现象 | 先判断 | 处置 |
|---|---|---|---|
| 1 | 场务说没收到检票提醒 | 先看 `GET /records?ticketNo=`：两通道各自什么状态 | INBOX 成功→让场务用**本人工号**登录看站内信（常是登错账号）；EMAIL FAILED→按第 2 条处理 |
| 2 | 邮件记录 `FAILED` | 邮件网关故障连续 3 次（首发+2 重试）都没成功 | 网关恢复后 `POST /records/{id}/retry` 一键补达；多条失败让运维先确认网关再逐条/分批重发 |
| 3 | 邮件记录 `RETRYING` 卡着不动 | 正常，退避到点由每分钟定时任务自动续投；看 `nextRetryTime` | 到点仍不推进看应用日志与网关连通性；急用时可直接手动重发 |
| 3a | 邮件记录短暂停在 `PENDING` | **正常**：邮件已改异步外呼，检票瞬间站内信先到，邮件在独立线程发送或等首投兜底（默认 90s） | 超过约 1 分半仍 PENDING，说明外呼线程忙/进程重启过，定时任务会自动认领补发；急用可手动重发（系统会防重复） |
| 3b | 手动重发提示"正在发送中，请勿重复重发" | **正常且是去重生效**：记录正处 `SENDING` 在途（邮件网关响应慢），原子去重拦住了重复点击 | 不用再点，等几十秒刷新；超 90s 仍卡 `SENDING` 说明外呼线程崩溃，定时任务会自动回收续投（不丢信） |
| 4 | 记录 `SKIPPED`，错误"收件人无邮箱" | 该场务只录了工号、没录邮箱 | 要收邮件就在收件人管理补邮箱（`PUT /recipients/{id}`）；只看站内信可忽略，不算故障 |
| 5 | 新增场务收不到通知 | 收件人没建、被停用（enabled=0），或检票时该人尚未建档 | 在收件人管理新增/启用（工号与登录名一致才能收站内信）；**只对之后的检票生效，不补发历史票** |
| 6 | 想改通知措辞/联系信息 | 直接改模板或收件人 | 放心改：模板保存自动升版本，**已发出的信和邮件内容原样保留**，新版只影响之后的检票 |
| 7 | 检票后一条通知都没有 | 总开关关了、模板/收件人全停用，或检票本身失败 | 查配置 `evops.notify.enabled`、`inbox-enabled`、`email-enabled`；查模板 enabled=1、收件人启用；检票接口是否成功 |
| 8 | 同一张票反复操作，通知发几遍 | 通知按"事件+票"幂等，只发一批 | 若观察到多批，按 requestId 查是否走了非常规补录入口；正常检票/重放都不会重复 |
| 9 | 站内信点开不是自己的信/看不到别人的 | 设计如此：按登录工号隔离 | 需代查走管理端发送记录（`/records`），不要借用场务账号 |
| 10 | 统计数字与邮件网关对不上 | 先分清 SUCCESS 与 SKIPPED；再看是否有 FAILED 已补达 | 站内信按记录数；邮件"成功数"应与网关实收一致（补达也计入），拒收次数=失败期投递次数 |

## 给运维的定位要点

- 配置（均可用环境变量覆盖）：
  - `EVOPS_NOTIFY_ENABLED` 总开关、`EVOPS_NOTIFY_INBOX` / `EVOPS_NOTIFY_EMAIL` 通道开关；
  - `EVOPS_NOTIFY_EMAIL_ENDPOINT` **邮件出口网关地址（上线必改，指向企业网关）**；
  - `max-retry=2`（验收口径，不含首发）、退避 `base-backoff-seconds=10`/`max-backoff-seconds=300`；
  - 时效：`EVOPS_NOTIFY_EMAIL_ASYNC`（默认 true，邮件异步外呼不卡检票；故障时可置 false 切回同步）、
    `EVOPS_NOTIFY_EMAIL_POOL_SIZE`（默认 2）、
    `EVOPS_NOTIFY_PENDING_FIRST_DELIVERY_SECONDS`（首投兜底时限默认 90s）。
- 数据表：模板 `t_notify_template`（文案版本看 `tpl_version`，与乐观锁 `version` 不是一回事）、
  收件人 `t_notify_recipient`、批次 `t_notify_dispatch`、逐通道记录 `t_notify_record`、
  站内信 `t_inbox_message`（`record_id` 唯一，重试不产生重复信）。
- 关键日志关键字：`检票通知批次完成`、`检票通知投递失败，第 N 次重试排期`、
  `检票通知重试 2 次耗尽置 FAILED`、`检票通知失败重试本轮处理 N 条`。
- 重试由每分钟定时任务扫描 `RETRYING 且 next_retry_time 到期` 的记录（索引 `idx_notify_rec_retry`）；
  单条异常不影响整批。
- **在途去重（2026-09-26 修复）**：发送记录新增中间态 `SENDING`（投递中，租约写在 `next_retry_time`）。
  异步首投/定时续投/人工重发/崩溃回收都先做数据库原子认领（CAS）把记录占成 `SENDING`，同一时刻只有一个执行方真正外呼，
  成功后落 `SUCCESS`、失败落 `RETRYING/FAILED`。因此**在途时再点"手动重发"会得到"该通知正在发送中，请勿重复重发"的提示，
  不会再发一封**；外呼线程崩溃则停在 `SENDING`，租约到期（默认 90s）由定时任务自动回收续投，不丢信。
  仅在网络长时间无任何响应、超过投递租约的极端情况下可能补投一次（以 messageId/票号核对即可），不再是过去那种必现的并发重复。
- 演示用的内置网关桩 `/mail-stub/**` 不鉴权、内存存邮件（重启清空）；生产部署邮件走真实网关，
  如无演练需要可移除 `MailStubController`。
- 版本：通知模块为 Flyway **V4**，启动日志应见「Schema 台账对账一致 …[1, 2, 3, 4]… flyway-4」；
  对账 ERROR 先别营业，按既有 Schema 对账流程处理。

## 绝对不要做

- 不要直接改 `t_notify_record` 里的 `title_rendered/content_rendered` 冒充"已发内容"——那是留档凭证。
- 不要为让某条失败立刻消失而手改状态为 SUCCESS；走"手动重发"拿真实回执。
- 不要把 `max-retry` 调成 0 来"消除重试告警"；验收口径固定失败重试 2 次，告警要靠修网关消除。
- 不要在生产把邮件网关地址留在 `localhost:8080/mail-stub`（桩只投本机内存，外面根本收不到）。
