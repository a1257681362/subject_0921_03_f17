# 数据库表结构初始化失败 · 值班处置（一页速查）

> 适用：新环境初始化、版本升级（Flyway 自动建表/改表）时，应用启动到一半失败，
> 或重启报 "Detected failed migration" / "对象已存在" / 台账与结构对不上。

## 先说结论（2026-09 起）

- **建到一半失败，直接重启即可续建，不需要手工删表、不需要手工改版本表。**
  启动时系统会自动清掉上一次的"失败记录"，再用全幂等脚本把半成品库补齐到最新
  （建表都是 `IF NOT EXISTS`、初始化数据都是 `MERGE`，已建对象自动跳过，不会重复、不报错）。
- 正常启动日志末尾应见：
  `Schema 台账对账一致：Flyway 成功版本 N 个 [...]，旧台账标记 M 个 [...]；增量物理对象抽查通过。`

## 为什么以前会"卡住、报对象已存在"

- 表结构在 H2 文件库里，建表语句一旦执行就落盘，**中途失败不会自动撤回已建的半张表**；
- 同时版本台账会留一条"失败"记录，不处理直接重跑会被它挡在最前面，脚本里的
  `IF NOT EXISTS` 根本没机会执行——于是看起来"对象已存在、版本对不上"。
- 现在这一步由 `FailedMigrationRecovery` 在每次正式迁移前自动处理。

## 标准处置

| 情况 | 做法 |
|---|---|
| 新环境/升级启动到一半失败（断电、磁盘满、脚本有 bug 等） | 排除外部原因后**直接重启**；日志出现"检测到上次 Flyway 迁移失败的残留记录…已删除…由幂等脚本自动续建"即为自愈生效 |
| 重启后仍在同一语句失败 | 说明是**脚本本身的缺陷**（不是半成品问题），自愈不会粉饰：保留现场、把启动报错（含版本号 Vn、SQL、行号）报研发，修脚本后再重启。**不要手工删业务表** |
| 启动报 `Migration checksum mismatch` | 有人**改动了已经执行过的版本脚本**。这是被明确禁止的；把脚本改回原样（变更只能新增 V<n+1>），或在研发指导下处理。自愈不会删除成功记录来"绕过"它 |
| 启动日志 `Schema 台账对账不一致`（ERROR） | 现场默认只告警不阻断营业；但**升级窗口内出现必须先查清楚再放量**，按错误提示核对对应版本对象/双写标记 |

## 红线（绝对不要做）

- 不要手工 `DROP` 业务表来"让它重建"——可能删掉真实存量数据。
- 不要直接删/改 `flyway_schema_history` 里 `success=TRUE` 的成功行，也不要改已发布的 `V*.sql`
  来"对齐"；成功版本有校验和（checksum）保护，改了会被启动拦截。
- 表结构变更一律走"新增版本脚本 `db/migration/V<n+1>__xxx.sql`"，不允许原地改历史脚本。

## 现场自检（需要时让运维执行）

```sql
-- 1) 是否有失败版本（正常应为 0 行）
SELECT installed_rank, version, description, script FROM flyway_schema_history WHERE success = FALSE;
-- 2) 成功版本清单（应连续到当前最新版本，基线 V1 类型为 BASELINE 或 SQL）
SELECT version, description, type, success FROM flyway_schema_history ORDER BY installed_rank;
```

> 自愈只处理第 1 步查到的失败行；第 2 步的成功行任何情况下都不会被自动删除或改校验和。
